## 2. 核心逻辑（这是全项目最重要的一节）

### 2.1 一句话

> **照片只能告诉你形状，不能告诉你克数。**
> 而本项目**不做任何称重、量杯、密度标定**，所以不走几何测量路线。

**克数的三条来源，按优先级：**

```
① 用户明确说了克数  → 直接采用（最高优先）
② 记忆库命中        → 采用历史值
③ AI 判断份量档位   → 查档位表得克数
```

### 2.2 为什么不做几何测量

几何路径需要：手表当参照 → 量容器 → 量填充高度 → 乘密度。
其中「容器容积」和「密度/空隙率」都**无法在无实测条件下标定**，误差连乘后约 **±45%**。

而 AI 直接判断档位的误差是 **±25~30%**。

> **一层猜测胜过四层猜测相乘。**

所以：**没有几何计算，没有密度表，没有手表标定，没有正视图。**

### 2.3 AI 只做两件事

```
① 这是什么东西（识别 → 匹配成分表）
② 是小份 / 中份 / 大份（相对判断）
```

**禁止 AI 输出克数、热量、任何营养数值。**

原因：AI 对「相对大小」判断可靠，对「数值换算」不可靠且不稳定。让同一碗饭每天输出 150 / 182 / 210 三个数，趋势就废了。

### 2.4 档位表（常量，代码内维护）

| 食物类别 | 小份 | 中份 | 大份 |
| --- | --- | --- | --- |
| 米饭 | 100 g | 150 g | 200 g |
| 面条（熟） | 180 g | 250 g | 320 g |
| 粥 | 200 g | 300 g | 400 g |
| 炒青菜 | 120 g | 200 g | 300 g |
| 炒菜（带肉） | 150 g | 220 g | 300 g |
| 肉类（单份） | 80 g | 120 g | 180 g |
| 汤 | 200 g | 300 g | 400 g |
| 水果 | 100 g | 170 g | 250 g |
| 面包 | 30 g | 50 g | 80 g |
| 饮品 | 200 g | 250 g | 330 g |

> 全部是「市面上常见的一份」，属常识量，不需要称重。可直接调整。

### 2.5 记忆库是精度的真正来源

```
第 1 次遇到某食物：AI 判档位 → 用户改一次 → 存进记忆库
第 2 次起：        直接命中记忆 → 零操作
```

**精度曲线：**

```
首次     ±25~30%
第二次起  ±5%
长期      ≈ 0
日总量    ±10~15%（多餐互相抵消）
```

### 2.6 复合菜：拆解，不查表

「宫保鸡丁」在成分表里查不到（这是事实，不是缺陷——每家做法都不同）。

**做法是拆成原料+调料逐条查表：**

```
番茄炒蛋
  ├ 番茄      200 g   ← 档位查表
  ├ 鸡蛋      100 g   ← 2 个 × 50 g（常量）
  ├ 食用油    13.8 g  ← 1 汤匙（常量换算）
  └ 盐 / 糖    3 g
```

**油盐糖的换算表是物理常量，零测量成本，却贡献了 90~180 kcal——这是本项目最大的精度收益点。**

## 5. 数据层

### 5.1 食物成分表

**来源**：`data-src/food_composition_full.csv`
衍生自《中国食物成分表 标准版（第 6 版）》第二册「各类食物一般营养成分」。

> 数据来源为公开项目 `china-food-composition-data`（视觉模型双识别 + 人工复核）。
> **自用无问题；若涉及商用分发，需自行确认《中国食物成分表》的引用合规性。**

| 项 | 实测值 |
| --- | --- |
| 记录数 | **1677** |
| 分类 | 61 个二级分类 / 15 个一级类别 |
| 列数 | 36 |
| 有英文名 | 1242（74.1%） |
| `edible` 可食部 < 100% | 699 条 |

**字段覆盖率**

| 字段 | 可解析为数值 |
| --- | --- |
| edible | 99.9% |
| energyKCal | 98.0% |
| protein / fat / CHO | 96.7~97.9% |
| water | 96.2% |
| ash | 92.6% |
| Na / K / Ca / Fe | 91.7~95.5% |
| dietaryFiber | 81.8% |

### 5.2 清洗规则（`scripts/build-foods.mjs` 必须实现）

| 原始值 | 含义 | 处理 |
| --- | --- | --- |
| `—` | 未检出 / 无数据 | → `null` |
| `Tr` | 微量 trace | → `0`，另存 `raw: "Tr"` |
| `899*` `900*` | 带星号 = **计算值**（油脂类多为 899） | 去星号 → `899`，标 `calculated: true` |
| `un` | 未知 | → `null` |
| 空串 | 缺失 | → `null` |
| 成分合计 > 105 g/100g | 原表异常（4 条） | 保留，标 `quality: "suspect"` |

### 5.3 三个必须处理的坑

**① 生熟差异 3 倍**

| foodCode | 名称 | kcal/100g |
| --- | --- | --- |
| 011305x | 面条（生，代表值） | **301** |
| 011317 | 面条（富强粉，煮） | **107** |
| 012401x | 米饭（蒸，代表值） | 116 |

> 检索结果**必须把状态（生/熟/干/蒸/煮/罐头）显示给用户**，不允许静默选一个。

**② 可食部 `edible`**

成分表热量是「每 100 g **可食部**」。

- 克数按可食部计算 → **不乘** `edible/100`
- 用户按带骨/带壳整体计量 → **必须乘** `edible/100`
- 因此克数字段带标记：`basis: "edible" | "as_purchased"`

**③ 中餐菜肴不存在**

实测命中数：宫保鸡丁 **0**、包子 **0**、饺子 **0**、奶茶 **0**、火锅 **0**。

> 这份数据是**原料库**，不是菜肴库。复合菜走 §2.6 的拆解路径。

### 5.4 检索索引（内存，不进数据库）

**1677 条这个量级，任何索引都是过度设计。** 全量加载进内存，遍历过滤，0.1~0.5 ms。

```ts
interface FoodIndex {
  all: FoodItem[];
  byCode: Map<string, FoodItem>;
  // 预计算：拼音全拼、首字母、字符 bigram、别名数组
  searchKeys: Map<string, string[]>;
}
```

**匹配打分（从高到低）**

```
1.00  完全同名
0.90  别名命中
0.80  拼音全拼 / 首字母完全相同
0.70  名称包含查询词
0.50  字符 bigram 重合度
0.30  主料 token 命中（拆解路径）
```

**加载时机：懒加载。** 进搜索页才解析 `foods.json`，不在启动时做。

### 5.6 Dexie Schema

```ts
// src/data/db.ts
export class FoodDB extends Dexie {
  diary!: Table<DiaryEntry, string>;
  memory!: Table<MemoryItem, string>;
  photos!: Table<PhotoRef, string>;
  settings!: Table<Setting, string>;

  constructor() {
    super('food-island');
    this.version(1).stores({
      diary: 'id, date, [date+meal], createdAt',
      memory: 'id, foodKey, [foodKey+scene], lastUsedAt',
      photos: 'id, entryId, createdAt',
      settings: 'key',
    });
  }
}
```

**四张表：**

```ts
interface DiaryEntry {
  id: string;
  date: string;                  // 'YYYY-MM-DD'
  meal: 'breakfast' | 'lunch' | 'dinner' | 'snack';
  foodCode: string | null;       // 命中成分表才有
  name: string;                  // 显示名（快照，不随成分表更新而变）
  grams: number;
  basis: 'edible' | 'as_purchased';
  portion?: 'small' | 'medium' | 'large';
  nutrients: NutrientSnapshot;   // 已按克数折算的「实际摄入量」
  scene?: string;                // 'home' | 'takeout:某店' | ...
  photoId?: string;
  source: 'photo' | 'text' | 'search' | 'memory' | 'manual';
  createdAt: number;
}

interface NutrientSnapshot {
  kcal: number; protein: number; fat: number; carb: number;
  fiber?: number; sodium?: number;
  // 其余 30 项按需，全部可为 null
  [k: string]: number | null | undefined;
}

interface MemoryItem {
  id: string;
  foodKey: string;               // foodCode，或 name:<归一化食物名>
  name: string;                  // 显示名快照
  scene: string;                 // 暂无则 'unknown'
  grams: number;
  portion?: 'small' | 'medium' | 'large';
  usedCount: number;
  corrections: number;           // 被用户改过几次
  lastUsedAt: number;
}

interface PhotoRef {
  id: string;
  entryId: string;
  relPath: string;               // 'photos/2026/11/xxx.jpg'（相对，不存绝对路径）
  width: number; height: number; bytes: number;
  createdAt: number;
}

interface Setting { key: string; value: unknown; }
```

### 5.7 关键设计：日记快照营养值

```
✗ 错误：diary 只存 foodCode + grams，显示时 join 成分表
✓ 正确：diary 存 foodCode + grams + 当时的营养快照
```

**原因**：成分表以后会修订。若 join，三个月前的记录会随数据更新而静默变化，历史趋势失真。

### 5.8 图片存储

| 项 | 决定 |
| --- | --- |
| 存原图 | ❌ |
| 存压缩图 | ✅ 长边 800 px、JPEG 0.8（约 100~150 KB） |
| 存哪 | App 私有目录 `Directory.Data` → `photos/YYYY/MM/<uuid>.jpg` |
| 数据库存 | 只存**相对路径** |
| 体积 | 一天 3 张 ≈ 360 KB，一年 ≈ 130 MB |

**为什么是 800 px**：DeepSeek 视觉模型会自动缩放到约 800×800 等效，超出部分丢弃。存更大对 AI 无用，对回忆也过剩。

**两个必须处理的技术点：**

```ts
// ① WebView 不能直接加载 file://
const uri = await Filesystem.getUri({ path: relPath, directory: Directory.Data });
const url = Capacitor.convertFileSrc(uri.uri);

// ② 删除记录时同步删文件，避免孤儿
await db.transaction('rw', db.diary, db.photos, async () => { ... });
```

**孤儿清理**：启动时（每月一次）扫 `photos/` 目录，删除不在 `photos` 表中的文件。
保守策略：只删「不在表里」且「写入超过 24 小时」的文件（避免误删刚拍还没保存的那张）；
反向也会清掉「表里有引用但文件已丢」的残行。实现见 `src/services/photoCleanup.ts`。

### 6.3 识别调用契约

**输入**：压缩后的照片（base64 data URL）+ 提示词
**输出**：严格 JSON

```json
{
  "items": [
    {
      "name_cn": "米饭",
      "name_en": "steamed rice",
      "category": "米饭",
      "portion": "medium",
      "is_composite": false,
      "confidence": 0.85
    },
    {
      "name_cn": "番茄炒蛋",
      "category": "炒菜（带肉）",
      "portion": "medium",
      "is_composite": true,
      "components": [
        { "name_cn": "番茄", "grams_hint": 200 },
        { "name_cn": "鸡蛋", "grams_hint": 100 },
        { "name_cn": "食用油", "tbsp": 1 }
      ],
      "confidence": 0.7
    }
  ]
}
```

**校验规则（客户端）**

- `portion` 必须是三档之一，否则视为 `medium`
- `category` 必须命中档位表，否则按「炒菜（带肉）」兜底
- `confidence < 0.5` → UI 标「估算，建议确认」
- 任何字段缺失都不得导致崩溃

### 6.4 提示词（v1 草稿）

```
你在帮我记录饮食。看这张照片，只做两件事，不要做别的。

1. 识别里面有哪些食物（最多 6 种）。用中文常见名字。
2. 对每个食物判断份量是小份、中份还是大份。

规则：
- 只输出 JSON，不要任何解释文字。
- 不要计算热量，不要给克数，不要给营养值。
- 如果是多种食材混在一起的菜（如番茄炒蛋、青椒肉丝），
  标 is_composite=true，并在 components 里列出主要原料和大致用量。
- 拿不准的，confidence 给低值（0.3~0.5），不要编。
- category 只能从这些里选：
  米饭 / 面条（熟）/ 粥 / 炒青菜 / 炒菜（带肉）/ 肉类（单份）/
  汤 / 水果 / 面包 / 饮品

份量参考：
- 小份 = 明显少于常规一份（约一个拳头的一半）
- 中份 = 常规一份
- 大份 = 明显多于常规一份（或加了饭/加了面）
```

**文字解析提示词**（无图时）：

```
把这句话拆成食物条目，只输出 JSON。

规则：
- 用户明确说了重量的，务必原样提取到 grams 字段。
- 「两」按 1 两 = 50 克换算。
- 「一碗/一盘/一个」这类没给克数的，只填 portion，不要猜克数。
- 数字可用阿拉伯数字或中文数字。

示例：
输入：中午吃了二两米饭、一碗番茄蛋汤、两个鸡蛋
输出：{"items":[
  {"name_cn":"米饭","grams":100},
  {"name_cn":"番茄蛋汤","portion":"medium"},
  {"name_cn":"鸡蛋","grams":100}
]}
```

### 6.5 降级策略

```
无 API Key       → 只能手动录入 / 搜索 / 记忆复用（功能完整，只是没有拍照）
请求失败         → 提示 + 保留照片 + 允许重试
识别结果为空     → 落到「手动搜索」页，并把照片留着
超时（>20s）    → 中断，提示「网络慢，可稍后重试」
```

**AI 是增强层，不是基础层。** 断网、欠费、Key 失效都不能让 App 不可用。

## 7. 录入流程

### 7.1 入口

底部导航中间的悬浮「+」按钮 → 打开录入 Sheet。

### 7.2 四条路径（按成本从低到高）

```
① 常吃 / 记忆    点一下历史记录     零操作，最常用
② 文字           打一句「二两米饭」  快
③ 拍照           拍一张 + AI 识别   稍慢
④ 手动搜索       搜成分表           兜底
```

**UI 顺序必须是 ① → ② → ③ → ④**，不要一进来就逼用户拍照。

### 7.3 文字解析流程

```
用户输入文字
  ↓
本地正则先试（快、免费、可预测）
  ├ 命中「数字 + 克/g」→ 直接取克数
  ├ 命中「数字 + 两」  → ×50
  ├ 命中「数字 + 个/碗/杯」→ 数量 × 常量
  └ 没命中 → 走 AI 解析
  ↓
食物名 → 本地检索匹配 → 用户确认
  ↓
写入日记 + 写记忆
```

**本地正则优先于 AI**：因为「二两米饭」这类表达规则极其固定，正则准确率 100%，还省一次 API 调用。

### 7.4 拍照流程

> **原则：照片先存档，分析后补。** 拍照即建一条 `pending` 记录（只有照片、grams=0），
> 之后 AI 识别成功与否都不影响原图。避免「网络抖一下、图没了、饭已经吃了一半」的情况。

```
拍照 / 选图
  ↓
压缩到长边 800 / JPEG 0.8
  ↓
存文件到 photos/YYYY/MM/
  ↓
【立刻】建一条 pending 记录（foodCode=null, grams=0, photoId 已挂）
       ↑ 到这一步照片就安全了，可以关掉 App
  ↓
（可选，P5-B）调 AI 识别 → 结果填回这条记录
  ↓
用户随时回来补：挑食物 → 档位/克数 → 保存（pending 清除）
  ↓
删记录 → 图片引用与文件一起删
```

## 8. 计算与精度

### 8.1 克数

```
用户给了克数 → grams = 用户值
记忆命中     → grams = 记忆值
只给档位     → grams = 档位表[category][portion]
```

### 8.2 营养

```
nutrients = per100 × grams / 100
```

若 `basis = 'as_purchased'`：

```
可用克数 = grams × edible / 100
nutrients = per100 × 可用克数 / 100
```

### 8.3 常量换算表（物理常量，可硬编码）

| 量具 | 容量 | 重量 | 依据 |
| --- | --- | --- | --- |
| 1 汤匙 植物油 | 15 ml | 13.8 g | ρ=0.92 |
| 1 汤匙 白砂糖 | 15 ml | 12.8 g | ρ=0.85 |
| 1 汤匙 酱油 | 15 ml | 17.5 g | ρ=1.16 |
| 1 汤匙 蚝油 | 15 ml | 19 g | ρ=1.27 |
| 1 汤匙 醋 | 15 ml | 15 g | ρ=1.00 |
| 1 茶匙 食盐 | 5 ml | 6 g | ρ=1.20 |
| 1 两 | — | **50 g** | 中国市制 |

### 8.4 精度预算

| 场景 | 误差 |
| --- | --- |
| 用户明确给克数 | ~0% |
| 记忆命中 | ±5% |
| AI 判档位（首次） | ±25~30% |
| 复合菜拆解 + 常量油糖 | ±20% |
| **日总量（多餐抵消）** | **±10~15%** |

> 对「参考与大致统计」的定位完全够用。关心的是「这周比上周多 200 kcal」，不是「今天精确 1837 kcal」。

| 能力 | 插件 | 注意 |

| 安全区 | CSS | `env(safe-area-inset-*)` |
| 视口高度 | CSS | 用 `100dvh`，**不用 `100vh`** |

### 返回键处理（Android 必须有）

```ts
App.addListener('backButton', () => {
  if (sheetOpen) { closeSheet(); return; }
  if (route !== '/today') { navigate('/today'); return; }
  App.exitApp();
});
```

不做这个，用户按返回键会直接退到桌面，体验很差。

### 权限声明（`android/app/src/main/AndroidManifest.xml`）

```xml
<uses-permission android:name="android.permission.CAMERA"/>
<uses-permission android:name="android.permission.READ_MEDIA_IMAGES"/>
```

Android 13+ 用 `READ_MEDIA_IMAGES`；更低版本用 `READ_EXTERNAL_STORAGE`。

```bash

npm install

```

### 签名（重要）

第一次打 release 前生成一次 keystore，**妥善保存**：

```bash
keytool -genkey -v -keystore food-island.keystore \
  -alias foodisland -keyalg RSA -keysize 2048 -validity 10000
```

换签名会导致覆盖安装失败、必须卸载 → **本地数据全丢**。

## 11. 里程碑

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| **P1 数据层** | CSV → foods.json + 检索索引 | 搜「西红柿」出番茄；搜「mifan」出米饭 |
| **P2 记录层** | 手动录入 + 每日汇总 | 不接 AI 也能完整记录一天 |
| **P3 记忆层** | 一键复用 + 修正回写 | 同一食物第二次记录零操作 |
| **P4 解析层** | 文字 → 克数（正则 + AI） | 「二两米饭一个鸡蛋」正确解析 |
| **P5 AI 层** | 拍照识别 + 档位 | 拍一碗饭能识别并给出中份 |

> **P1~P3 完全不依赖 AI，可先独立跑通。** AI 是事后增强。
> 这个顺序的意义是：即使 AI 这块最后不做了，App 也已经可用。

## 12. 已知风险

| # | 风险 | 应对 |
| --- | --- | --- |
| 1 | DeepSeek 对中式菜品识别粗（800×800 有效分辨率） | 细粒度靠记忆库，不靠视觉 |
